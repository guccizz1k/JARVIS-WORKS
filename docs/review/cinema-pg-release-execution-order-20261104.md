# JARVIS-WORKS — 확정 실행 순서 및 수락 게이트 (2026-11-04)

목적: **진행 순서 보존**, 이미 완료된 검증의 중복 방지, 정확한 완료 판정.
적용 범위: CINEMA × PostgreSQL 검토 브랜치. 원본 CINEMA HTML, `app/main.py`, `app/static/`, 기존 비즈니스 API·테이블·데이터는 승인 없이 변경하지 않는다.

## 실행 순서 (고정)

1. **S4 단일 거래 원장·중복 방지**: CINEMA 신규 거래를 단일 쓰기 경로로 하고, v92 실거래 행이 있는 테넌트의 신규 원장 쓰기를 거부. 기존 v92 POST와 신규 POST의 동시 활성화 차단, 과거 거래 연결·정합성(승인된 출처 관계) 설계 및 테스트. 단순 POST 라우트 차단은 S4 전체 PASS가 아님. 여러 서버/동시성까지 차단할 DB 원자성·출처 검증 필요.
2. **개발 PostgreSQL 17의 신규 역할·ACL·FORCE RLS**: 대상은 `jarvis-works-dev` 만. 원본 업무 테이블 무변경, 소유자/작성자 권한 분리, 외부 노출 금지, 개발 데이터 무결성·차단 검사. **DB 마이그레이션 도구 안전 검사 차단 시 우회하지 않고 BLOCKED**.
3. **실제 HTTPS API·증빙·거래 E2E**: 로그인/MFA → CSRF/기업 격리 → 견적 → 수주 → 납품 증빙 업로드·관리자 열람 → 명세 → 청구 → 내부 입금, 중복/동시성/실패 롤백 및 잘못된 권한 시험. 모의 HTTP 또는 격리 SQL의 PASS를 실제 HTTPS E2E로 둔갑하지 않는다.
4. **기업 메신저 서버 연결 + 자동화**: 거래처↔가입 기업 매핑을 권한 확인 후 만들고, 전송·첨부·검색/스크롤·감사 시험. 기존 v2 안전 차단 우회 금지. 규칙 저장·승인·중복 실행 방지·실패 복구는 독립 검증 후 활성화.
5. **OCR 실제 문서 정확도 + 운영 품질**: 적법한 독립 원본 50건 및 정답표(서식 다양성), 필드별 오류/거부율 실측. 민감 원본은 PUBLIC GitHub와 외부 API에 올리지 않는다. 복원(RPO/RTO)·부하(P95/P99)·PC 브라우저 프레임/동작 측정.
6. **Render 격리 스테이징 + 독립 감사 및 최종 출시 게이트**: 보호된 Render 서비스의 현재 브랜치/Secrets와 시나리오를 확인하고 허용된 검증만 배포. 독립 보안 QA, 전체 회귀, DB 격리, 재시작·복구 후 증거를 수집. `main` 병합·운영 데이터 이전·정식 출시에는 별도의 최종 승인 필요.

## 작업 방식 및 판정

- 다음 단계는 이전 단계의 **실제 검증 결과가 PASS일 때** 순차 실행하되, 안전하게 격리할 수 있는 독립 테스트와 설계는 병행할 수 있다.
- 5-Gate: (1) 문법·의존성 (2) 기능·금액 정확성 (3) 기존 기능/데이터 회귀 (4) UI·접근성 (5) 운영·보안·성능·복구.
- 판정: PASS / PARTIAL / FAIL / BLOCKED / NOT RUN / NOT MEASURED. 근거 없는 PASS, 완료율, 자동 배포 금지.
- S4 검증 상태: 동일 서버의 v92/CINEMA POST 동시 활성화 차단은 기검증. v92 기존 거래 행이 있는 테넌트의 신규 원장 접근은 **추가 코드와 격리 테스트 필요**. 다른 서버/프로세스 동시 기록, 중복 기원 식별, 자동 연결·정산의 단일 출처는 **미완성/차단**.
- DB 영구 변경: 사전 SQL 롤백 시험 성공했으나 실제 migration 요청은 안전 검토에서 차단됨. 우회해서 진행하지 않음.
- 최신 증거는 PR #139과 해당 SHA의 GitHub Actions 로그에서 확인한다. 모든 게이트를 **같은 HEAD**로 다시 검증한다.
