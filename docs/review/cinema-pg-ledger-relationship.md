# CINEMA 거래 원장(`cinema_pg_*`) ↔ 기존 v92 계열 원장 관계 분석 (감사 S4) 및 메신저·자동화 연동 설계 공백

상태 표기: PASS / PARTIAL / FAIL / BLOCKED / NOT RUN / NOT MEASURED. 이 문서는 **분석과 결정 요청**이며, DB에 어떤 것도 적용하지 않았습니다.

## 1. 두 원장이 겹치는 부분 (코드에서 확인한 사실)

| 개념 | 기존(v84/v92 계열, `jw_dev.*`) | 신규 `cinema_pg_*` |
|---|---|---|
| 거래처 | `customers`(id, name, business_number …, 날짜는 text) | `cinema_pg_partners`(버전, 테넌트 RLS) |
| 견적 | `quotes`(`doc_no` = `Q-YYYYMMDD-<10자>`, 상태 text), `quote_items` | `cinema_pg_quotes`(`trade_no` = `TYYMMDD-NNNN`, 상태 전이 표) |
| 수주·청구·입금 | `orders`, `order_items`, `invoices`, `invoice_items`, `payments`(v84 조회, v145 미리보기, v161 잔액 미리보기) | `cinema_pg_orders/…/invoices/payments` + 반전(reversal) |
| 납품 | 검토 전용 영수증 `review_delivery_*_v151`(v154 검토 API, 납품 "게시" 없음) | `cinema_pg_deliveries` + 서버 보관 증빙 |
| 감사 | `audit_logs` | `cinema_pg_audit`(추가 전용) |

두 구조는 같은 업무 사슬(견적→수주→납품→명세→청구→입금)을 각자 따로 표현합니다. **어느 쪽이 "진실의 원천"인지는 아직 결정되지 않았습니다.**

## 2. 이번 후보가 보장하는 것 / 보장하지 않는 것

보장(검증됨):

* 신규 엔진은 기존 `jw_dev` 거래 테이블을 **읽지도 쓰지도 않습니다**(정적 계약 테스트 `test_engine_does_not_touch_existing_tables`와 `test_engine_references_no_existing_object_except_the_two_identity_functions` PASS; 엔진이 참조하는 기존 객체는 `stage_identity_v84()`, `current_org_from_session()` 두 함수뿐).
* 식별자는 서로 겹치지 않습니다: 신규 ID는 `cinema_pg_new_id()`의 무작위 값, 거래번호는 `T…`, 기존 견적번호는 `Q-…`. 브리지는 신규 거래를 `pg-` 접두 ID로만 표시(기존 거래와 ID 충돌 없음).
* v92 기반 스키마와 신규 엔진을 **같은 임시 DB에 함께 설치**한 상태에서 SQL 게이트 205건이 통과합니다(공존 확인; PG16.15 기준).

보장하지 않음(미결정·미검증):

* 같은 실제 거래가 양쪽에 중복 입력되는 것을 막는 장치는 **없습니다**(자동 연결·중복 검출 없음). 화면에서는 두 원장 거래가 나란히 보이며 합산 보고서를 만들면 이중 집계될 수 있습니다.
* 기존 대시보드·미수금 집계는 신규 원장을 포함하지 않습니다(의도적으로 수정하지 않음).
* 기존 DEV DB에 신규 SQL을 적용한 적이 없고, 적용 시의 마이그레이션·권한 영향은 측정하지 않았습니다.

## 3. 선택지와 권고 (사용자 결정 필요)

| 안 | 내용 | 장점 | 위험 |
|---|---|---|---|
| A (권고, 현 후보의 가정) | 신규 거래는 **cinema_pg 원장이 단독 원천**. v92 견적은 "초안·가져오기" 용도로만 유지하고 상호 변환 없음 | 기존 코드·DB 무수정, 단순 | 사용자가 두 곳에 같은 거래를 입력하면 중복 — 운영 규칙(어디서 입력할지) 필요 |
| B | 추가 전용 연결 테이블 `cinema_pg_v92_links`(v92 견적 id ↔ cinema 견적 id)와 읽기 전용 정합성 점검 함수 | 중복·불일치를 SQL로 탐지 | 새 마이그레이션·권한 승인 필요, 연결 의미 정의 필요 |
| C | v92 계열을 신규 엔진 위로 이관 | 단일 원천 | 기존 테이블·데이터 변경이 필요 → **금지 범위**, 별도 승인 없이는 불가 |

현재 코드는 A를 전제로 합니다. B·C는 사용자 승인 전에는 구현하지 않았습니다.

## 4. 메신저 서버 연동 — BLOCKED (이유)

* CINEMA 원본의 메신저 화면(`ROUTES.messenger`)은 **거래처(partner)별 로컬 메모 스레드**입니다(`DB.threads[partnerId]`, 화면 안내문도 "로컬 메신저입니다"). 서버의 v90 메신저는 **기업(조직) 간 채팅**(`POST /chats {other_org_id}`)입니다.
* 거래처 ↔ 상대 기업(조직) 매핑이 어디에도 정의돼 있지 않습니다. 매핑 없이 연결하면 잘못된 기업에 메시지가 가거나 존재하지 않는 대화를 보여 주게 됩니다(추측 연결 금지).
* 화면을 서버 데이터로 그리려면 `ROUTES.messenger`의 DOM을 다시 만들거나 가로채야 하는데, 이는 원본 UI 무수정 원칙과 충돌합니다. 또한 `cinema_bridge_v2.js`가 메시지 전송·파일 첨부를 문서 캡처 단계에서 의도적으로 차단하고 있어(수정 불가 파일) v3가 같은 이벤트를 재활성화하려면 `window` 캡처 우회가 필요합니다 — 기존 안전장치를 우회하는 변경이므로 승인 없이 하지 않습니다.
* 결정 필요: ① 거래처↔조직 매핑을 만들 것인지(신규 추가 전용 테이블 + 승인), ② 메신저 화면 변경을 허용할 것인지, ③ v2 차단 해제 방식. 이 결정 전까지 **NOT DONE / BLOCKED**, 현 차단 상태(안전)가 유지됩니다.

## 5. 업무 자동화 서버 연동 — BLOCKED (이유)

* 원본 자동화 화면은 로컬 규칙 스위치와 로컬 실행 기록(`DB.runs`)입니다. `cinema_bridge_v2.js`는 규칙을 모두 끈 상태로 두고 `#/automation` 클릭을 차단합니다(수정 불가).
* 요구된 규칙("승인 견적→수주 초안", "확인된 납품→명세표 초안", "확정은 사용자 승인")을 서버에서 실행하려면 ① 규칙 저장 테이블, ② 누구의 권한으로 실행하는지(직무 분리와 충돌 가능), ③ 실행 주체(트리거/작업자)가 필요합니다. 모두 설계 결정과 DB 변경 승인이 필요합니다.
* 현재 후보에서 이미 가능한 것: 견적 승인 후 **사용자가 버튼으로** 수주 생성, 납품 확인 후 **사용자가 버튼으로** 명세표 초안 생성(모두 서버 규칙으로 강제). 자동 실행은 없고 자동 확정도 없습니다.
* 결정 필요 후 진행: 규칙 테이블 신설 승인, 실행 주체 정책, 자동화 화면 차단 해제 범위.
