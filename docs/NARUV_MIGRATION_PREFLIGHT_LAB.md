## Risk inventory and design
- Wrong tenant/source/entity: current identifiers and target snapshot must match prior deterministic review; source_id must represent a stable logical source namespace in future integration, not just an export filename. This is consistency, not access control.
- Schema/order/alias changes: exact raw header digest, deterministic mapping and review binding reused. No guessing or silently dropping columns.
- Row width/count, malformed cells, numbers converted from string IDs, leading zero loss: strict bounded sequences and exact string types. No coercion or automatic repair. Conservative ASCII ID and NFC text restrictions are lab policy, not agreed production ERP compatibility. Reject formula-like prefixes, control/format/surrogate chars and outer whitespace; legitimate unsupported names require an explicit policy review. Business number is shape-only; no claim of registry/checksum verification. Optional None and empty string are distinct, preserved in the digest.
- Duplicate rows and target collisions: case-folded source-ID uniqueness within the explicit tenant/source/entity namespace. Reject conflicts rather than update/merge. Snapshot must contain all existing IDs for that scope. No foreign-key, business-number uniqueness, or database collation claim.
- Stale review/row change/target change: binding includes ordered exact rows, target revision, target identity set digest, row count. Recompute from current immutable input; do not authorize import. Hashes are not signatures or access tokens. Replay of an identical immutable plan is allowed for this pure read-only check; no actual write/idempotency guarantee.
- Resource limits: lab ceiling 1000 rows, 10000 existing IDs, 64 headers, bounded field lengths; reject excess rather than truncate. Future large-file parsing/streaming, ZIP bomb defenses, total memory/time bounds and production load tests separate. No raw row values in result or error messages. Hashes still require appropriate data access restrictions.
- Concurrency and crash recovery: pure function has no mutation or side effects. Caller must supply immutable/transaction-consistent inputs. Future real writer requires authenticated tenant and source, transactional snapshot fencing, per-tenant uniqueness and idempotency, RLS/FORCE RLS, durable journal, rollback, crash recovery and actual PG17 tests before any data write. No claim these are already implemented. Review expiry and server-side approval separate.

Five independent processes: retain existing 12+8 suites and run 14 new tests with 500 varied batches, 1500 negative controls, five max-size batches of 1000 and snapshots of 10000. No PASS claim until actual CI evidence. Main, existing product engine, database and deploy protected.
